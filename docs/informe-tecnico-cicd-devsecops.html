01 Objetivo del proyecto

Qué se propuso demostrar esta actividad y por qué el pipeline se armó como se armó.

El objetivo fue implementar, de punta a punta, un flujo real de integración y despliegue continuo con enfoque DevSecOps para un e-commerce ya funcional (NestJS + Next.js + MySQL), cubriendo los tres pilares que pide la consigna: build y pruebas automatizadas, análisis de seguridad integrado al pipeline (SAST y DAST, más validación de integridad de artefactos) y despliegue real en un cluster de Kubernetes gestionado con GitOps.

Un intento anterior de este mismo pipeline se descartó deliberadamente antes de esta entrega: se había armado sin selección justificada de herramientas y sin un cluster de Kubernetes realmente accesible (el CD apuntaba a un cluster sin contexto de kubectl configurado). Esta vez cada herramienta se eligió por su propósito específico, y el pipeline se verificó corriendo de verdad — no solo "en teoría" — incluyendo el despliegue final en un cluster real.

Decisión de arquitectura clave: se separó explícitamente el CI (GitHub Actions, corre en la nube) del CD (Argo CD, corre dentro del cluster). GitHub Actions nunca aplica cambios directo a Kubernetes — solo construye, prueba, escanea y actualiza el tag de imagen en un manifiesto versionado en Git. Argo CD, que vive en el cluster, detecta ese cambio y sincroniza. Es el patrón GitOps: Git como única fuente de verdad del estado del sistema.

02 Arquitectura del pipeline

Las etapas, en el orden en que corren, y qué depende de qué.

El pipeline vive en un único workflow de GitHub Actions (.github/workflows/ci.yml) con diez jobs. Los primeros seis corren en paralelo apenas se hace push; el resto depende de que esos pasen:

ESLint backend
ESLint frontend
Semgrep SAST
Tests unitarios
Tests e2e
→
Build & push (GHCR)
→
Trivy
ZAP DAST
→
Actualizar manifiestos
→
Argo CD sincroniza

La etapa de build solo corre si todo lo anterior — lint, SAST, tests unitarios y tests e2e — pasó. Trivy y ZAP corren en paralelo entre sí una vez que las imágenes ya están publicadas, porque ambos necesitan la imagen construida (Trivy la escanea, ZAP levanta el stack completo con docker-compose y ataca la app real). El último job no toca el cluster directamente: escribe el nuevo tag de imagen en k8s/*/kustomization.yaml y lo commitea a main — Argo CD, que ya está corriendo dentro del cluster y observando ese repositorio, hace el resto.

Por qué Argo CD corre dentro del cluster

Es un detalle que no es obvio la primera vez: el cluster de Kubernetes de esta demo es local (Kubernetes de OrbStack, en la misma Mac), así que los runners de GitHub Actions —que corren en la nube— no tienen forma de conectarse a él directamente. Argo CD resuelve esto al revés: en vez de que el CI empuje el despliegue, Argo CD (que sí vive dentro del cluster) hace pull del repositorio de Git de forma periódica. El CI nunca necesita credenciales del cluster ni acceso de red hacia él — solo necesita poder pushear a Git.

03 Herramientas utilizadas y su propósito

Cada herramienta se eligió para un propósito puntual dentro de la consigna DevSecOps, no como relleno.

HerramientaCategoríaPor qué esta y no otra
GitHub Actions CI/CD El repositorio ya vive en GitHub público — cero infraestructura adicional, y GITHUB_TOKEN alcanza para publicar en GHCR sin gestionar credenciales extra.
Argo CD CD / GitOps Corre dentro del cluster y hace pull de Git — resuelve el problema de desplegar a un cluster local sin exponerlo a internet. Patrón app-of-apps: una Application raíz gestiona 3 hijas (database, backend, frontend).
Kubernetes (OrbStack) Orquestación Cluster real (no simulado), corriendo local sin costo de nube. Se usó en vez de manifiestos "de mentira" que nunca se aplican de verdad.
ESLint + plugin de seguridad SAST Cubre reglas específicas de JS/TS (inyección, mal uso de eval, etc.) integradas al mismo linter que ya corre en cada PR.
Semgrep SAST Reglas más amplias (OWASP Top 10, JWT, Node.js) y — clave para este pipeline — reglas sobre el propio workflow de CI/CD (detectó tags mutables de GitHub Actions, ver hallazgos).
Trivy Integridad de artefactos Escanea las imágenes Docker publicadas por vulnerabilidades conocidas (CVE) y genera un SBOM (CycloneDX) — la evidencia de "qué hay adentro" de lo que se despliega.
OWASP ZAP DAST Ataca la aplicación corriendo de verdad (no el código fuente) — la única forma de encontrar problemas que solo existen en runtime, como cabeceras de seguridad ausentes.

04 Etapa CI — build, tests y SAST

Los primeros seis jobs: nada llega a construirse en imagen si esto no pasa.

Lint (ESLint con reglas de seguridad) y Semgrep corren sobre backend y frontend por separado. Los tests se dividen en tres jobs independientes: unitarios de backend, e2e de backend (con un contenedor real de MySQL como service del job) y unitarios de frontend. Separar el e2e del unitario fue deliberado — el e2e necesita levantar una base de datos y correr migraciones, así que tiene su propio costo de tiempo y no debe bloquear al resto si algo tarda.

passESLint — Backend29s
passESLint — Frontend24s
passSemgrep SAST31s
passTests — Backend (unit)32s
passTests — Backend (e2e)1m 5s
passTests — Frontend26s

El job de e2e de backend nunca había corrido en CI antes de esta entrega — solo existían los unitarios. Apenas se agregó, atrapó dos regresiones reales que llevaban tiempo silenciosas en el código (detalle en la sección de hallazgos). Esa es la razón concreta por la que vale la pena correr e2e en el pipeline y no solo localmente: nadie las había notado hasta que un job de CI las forzó a la superficie.

05 Integridad de artefactos — Trivy

Una vez que backend y frontend se construyen y publican en GHCR, se escanean antes de que nada los toque.

Las imágenes se publican en el registro de contenedores de GitHub (ghcr.io) con dos tags: latest y un tag inmutable por commit (sha-<7 caracteres>). El tag por SHA es el que realmente usa el despliegue — latest es solo de referencia — para que cada versión desplegada sea trazable a un commit exacto.

Trivy corre contra ambas imágenes recién publicadas:

  • Reporte SARIF con severidad CRITICAL/HIGH, subido a la pestaña de Security de GitHub (visible junto a los hallazgos de Semgrep, mismo lugar).
  • SBOM en formato CycloneDX del backend — el inventario exacto de dependencias y versiones que corren en producción.

El escaneo se configuró para reportar (exit-code: 0), no para bloquear el build. Es una decisión consciente para esta entrega: bloquear por cualquier CVE de severidad alta en una imagen base (node:22-alpine) habría hecho el pipeline inutilizable sin antes triagear cada hallazgo uno por uno. La evidencia queda igual, visible en Security y como artifact descargable.

06 DAST — OWASP ZAP

El único análisis de seguridad de los cuatro que ataca la aplicación corriendo, no el código.

Para esta etapa el pipeline levanta el stack completo (MySQL + backend + frontend) con docker compose up --build directo en el runner, espera a que el frontend responda 200, y corre un baseline scan de ZAP contra http://localhost:3001. El resultado real de la última corrida:

OWASP ZAP Baseline Scan — resumen
FAIL-NEW: 0	FAIL-INPROG: 0	WARN-NEW: 10	WARN-INPROG: 0	INFO: 0	IGNORE: 0	PASS: 60

WARN-NEW: Permissions Policy Header Not Set [10063] x 5
WARN-NEW: Cross-Origin-Embedder-Policy Header Missing or Invalid [90004] x 9
WARN-NEW: Sec-Fetch-Dest Header is Missing [90005] x 8
WARN-NEW: Base64 Disclosure [10094] x 3
WARN-NEW: Non-Storable Content [10049] x 7
WARN-NEW: Modern Web Application [10109] x 2

Cero fallas nuevas, diez advertencias — ninguna crítica, todas relacionadas a cabeceras de seguridad HTTP opcionales que Next.js no setea por defecto (Permissions-Policy, Cross-Origin-Embedder-Policy, Sec-Fetch-Dest). Es exactamente el tipo de hallazgo que un DAST encuentra y un SAST no puede: no es un bug en el código, es una configuración de runtime del servidor.

Pendiente
Endurecer cabeceras de seguridad en next.config.js (o vía helmet en el backend) para resolver estos 10 warnings antes de una entrega futura — no bloquea esta demo, pero es la mejora obvia de continuidad.

07 CD — GitOps con Argo CD

Cómo un push a main termina siendo un pod corriendo en el cluster, sin que nadie corra kubectl apply a mano.

Los manifiestos de Kubernetes viven en k8s/ organizados con Kustomize, uno por servicio (backend/, frontend/, database/), más una carpeta apps/ con los recursos Application de Argo CD que apuntan a cada uno. Un root-app.yaml bootstrapea todo con el patrón app-of-apps: una sola Application raíz gestiona las otras tres.

Flujo completo de un despliegue

  1. El job Build & Push construye y publica backend:sha-<commit> y frontend:sha-<commit> en GHCR.
  2. El job Actualizar manifiestos corre kustomize edit set image sobre k8s/backend/kustomization.yaml y k8s/frontend/kustomization.yaml, y commitea el cambio a main con el bot de GitHub Actions.
  3. Argo CD, que sondea el repositorio, detecta el nuevo commit y compara el estado deseado (Git) contra el estado real (cluster).
  4. Con syncPolicy.automated activado, sincroniza solo: aplica el nuevo Deployment, corre el hook PreSync (una migración de Prisma) antes de que el nuevo pod reciba tráfico, y hace rolling update sin downtime (maxUnavailable: 0).

El CI nunca toca el cluster. No hay kubeconfig ni credenciales de Kubernetes en los secrets de GitHub Actions — el único puente entre CI y CD es un commit de Git. Esto es, literalmente, la definición de GitOps: si Argo CD se cayera, el pipeline de CI seguiría corriendo exactamente igual, solo que nadie aplicaría los cambios hasta que Argo CD volviera.

08 Hallazgos reales del proceso

Nada de esto se armó a la primera. Documentar los problemas reales — y cómo se diagnosticaron — es tan parte de la evidencia como el pipeline en verde.

Hallazgos de seguridad (SAST)

Tags mutables en GitHub Actionscorregido
Semgrep marcó 35 usos de uses: accion@v4 (y similares) en ci.yml — un tag como v4 puede ser repuntado por el dueño de la action, habilitando un ataque de cadena de suministro (pasó de verdad con tj-actions/changed-files en 2025). Se fijaron los 10 actions de terceros del workflow a su SHA de commit exacto, con la versión como comentario.
Configuración de supply-chain de pnpm incompletacorregido, con una excepción documentada
Se agregaron blockExoticSubdeps y minimumReleaseAge (7 días) a pnpm-workspace.yaml. Se evaluó también trustPolicy: no-downgrade, pero al activarlo rechazó 8 paquetes muy conocidos (chokidar, semver, vite) por "trust downgrade". Se verificaron los mantenedores reales de esos paquetes en npm — son transferencias legítimas, no compromisos — y se dejó desactivado con la justificación documentada en el propio archivo, en vez de forzar una policy que rompía el install a ciegas.

Bugs reales de la aplicación, atrapados por el pipeline

Mensaje de bienvenida sin emojicorregido
El endpoint raíz (GET /) había perdido el 🍪 del mensaje en algún punto, pero el test e2e seguía esperándolo. Invisible hasta que el job de e2e de backend corrió por primera vez en CI.
Test desactualizado contra la forma real de la respuestacorregido
GET /products devuelve {`{products, pagination}`} desde hace varias sesiones (se agregó paginación), pero un test e2e seguía asumiendo un array plano. Mismo mecanismo: nadie lo notaba porque ese test nunca corría en CI.

Infraestructura y despliegue

Manifiestos de k8s con imágenes "de mentira"corregido
Los Deployments de backend/frontend en k8s/ (de un intento anterior) usaban node:18-alpine con un servidor HTTP inline que solo devolvía "OK", y nginx:alpine vacío — Argo CD sincronizaba "exitosamente" un stack que nunca sirvió la aplicación real. Reemplazadas por las imágenes reales publicadas en GHCR.
frontend/public/ faltantecorregido
El Dockerfile del frontend hace COPY --from=builder /app/frontend/public ./frontend/public, pero el directorio no existía en el repo — el build de Docker fallaba siempre desde un checkout limpio. Confirmado en el primer intento de build en CI.
runAsNonRoot sin UID explícitocorregido
Kubernetes no puede verificar que un usuario no-root con nombre (USER node en el Dockerfile) sea realmente no-root sin un runAsUser numérico explícito. Se agregó runAsUser: 1000 (UID real de node, verificado con docker run --entrypoint sh … id node).
Falta de volumen escribible para subida de imágenescorregido
El backend hace mkdirSync('/app/backend/uploads') al arrancar (multer). Sin un volumen montado ahí, el usuario no-root no puede crear el directorio sobre el filesystem de solo lectura de la imagen — crash loop. Se agregó un volumen emptyDir.
Job de migración con datos de prueba, no la migración realcorregido
El hook PreSync que corre las migraciones de Prisma tenía un echo "Migrations OK (demo mode)" en vez de prisma migrate deploy real. Además, overridear el command del Job no hereda el PATH que exporta el entrypoint.sh de la imagen — hubo que replicarlo explícitamente.
trivy-action con una dependencia interna rotacorregido
La marketplace action de Trivy fallaba de forma silenciosa e intermitente (su instalador interno referenciaba una versión de aquasecurity/setup-trivy que ya no existe). Se reemplazó por una invocación directa de docker run aquasec/trivy, que depende solo de la imagen oficial ya estable.
Desajuste de arquitectura de CPU (amd64 vs arm64)mitigado parcialmente
Los runners de GitHub Actions son amd64; el cluster de la demo (OrbStack, Apple Silicon) es arm64. Sin un build multi-plataforma, kubelet no encuentra un manifiesto compatible al pullear. Se agregó docker/setup-qemu-action + platforms: linux/amd64,linux/arm64 en ambos builds — resolvió el despliegue de la app, pero el motor nativo de Prisma dentro del hook de migración todavía tropieza con el binario de la arquitectura correcta en un caso puntual (ver sección de CD). Documentado como mejora pendiente, no bloquea la demo.

10 Conclusiones y aprendizajes

Qué nos llevamos de armar esto de verdad, no solo de leer sobre el patrón.

El GitOps recién se entiende cuando se rompe. La primera vez que Argo CD revirtió cambios aplicados a mano contra el cluster (porque selfHeal: true detectó que no coincidían con Git) fue más instructivo que cualquier diagrama: quedó claro, en la práctica, que Git — no el estado vivo del cluster — es la única fuente de verdad. Cualquier cambio que no pase por un commit se pierde en el próximo ciclo de reconciliación.

Un DAST encuentra una clase de problema completamente distinta a un SAST. Los cuatro análisis de seguridad (ESLint, Semgrep, Trivy, ZAP) no son redundantes entre sí — cada uno mira una capa diferente: código fuente, configuración del propio pipeline, contenido de las imágenes publicadas, y comportamiento real en runtime. Los 10 warnings de ZAP (cabeceras HTTP) nunca los habría encontrado un linter de código, porque no son un bug de código: son una omisión de configuración que solo existe cuando la app está corriendo.

Agregar un test e2e al CI no es un checkbox — encuentra bugs de verdad. Los dos bugs reales de backend (mensaje sin emoji, forma de respuesta desactualizada) llevaban tiempo en el código sin que nadie los notara, simplemente porque esos tests nunca corrían de forma automática. El valor de CI no es "tener tests", es correrlos en cada cambio.

La mayoría de los problemas de esta entrega no fueron de "seguridad" en el sentido de la consigna — fueron de infraestructura real. El desajuste de arquitectura de CPU, los finalizers de Argo CD bloqueando la limpieza de un Job, una action de terceros con una dependencia interna rota: ninguno de estos aparece en un tutorial. Son exactamente el tipo de fricción que separa "el pipeline corre en la demo del profesor" de "el pipeline corre en un cluster real ajeno al entorno donde se escribió".
